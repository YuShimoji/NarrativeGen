# SP-STUDIO-001: Studio Rebuild（エンジンの判断を見る作業場）

**Status**: partial | **Cat**: core / ui

## 1. 目的

2026-11-21のuser依頼「NarrativeGenを再起動し、作り変えるぐらいの再構築をしてほしい」に基づく。
userが挙げた課題（原文の要旨ではなく指摘点そのもの）:

1. 確認画面にJSONの中身が出がちで、エンジンが機能しているかの判断が難しく、視覚的にも見づらい。
2. ゲーム部分のシステムを同時開発していて、そちらを進めると全体がそちらへ没頭してしまう。
3. ウェブプレビューページのUIが洗練されておらず、ボタンまみれで使いづらい。

エンジンの思想は原初設計（Git履歴 `58af830^:docs/archive/legacy-specs/ORIGINAL_DESIGN_PHILOSOPHY.md`）の
「Entity中心のプロパティ駆動型ナラティブ生成」を保つ。人物の知識と物の性質の比較から違和感を検出し、
事象Entityを生み、それが後の文章と選択肢を変える。この因果を作者が画面で確かめられることを再構築の芯にする。

## 2. 構成（2026-11-21 user選択）

| 層 | 場所 | 責務 | 状態 |
|---|---|---|---|
| エンジン | `packages/engine-ts` | 世界（物と性質）・心（知識と違和感）・文章（展開と挿入）・流れ（条件と効果）・妥当性（検証と到達）を決定論で計算する。意味論は現行のまま | 維持 |
| 判断の記録 | `packages/engine-ts/src/trace.ts` | エンジンが下した判断を構造化した事実として返す。文言は持たない | 新設 |
| 作業場 | `apps/studio` | 記録を描く。JSONを画面に出さない。上部の操作は物語の選択・最初から・実行/点検の3つ | 新設 |
| ゲーム層 | Play演出・BGM・`packages/sdk-unity`・`apps/public-studio`・Sites adapter | 同じエンジンをmodel JSONとsession APIだけで使う | 凍結（userが「凍結して切り離す」を選択） |
| 旧作業場 | `apps/web-tester` | 制作・GUI編集・export等の既存機能 | 置き換えまで残す。新機能は足さない |

ゲーム層の凍結: 再構築中はゲーム層の機能追加・修正をしない。再開は別の作業単位として、エンジンとの接続
（model JSON・`startSession`/`getAvailableChoices`/`applyChoice`）を変えずに行う。エンジン側の変更が
接続を変える場合は、その変更の作業単位で判断を返す。

## 3. 判断の記録（trace）の契約

- `traceStart(model)` / `traceStep(session, model, choiceId)`: 実行時と同じ`startSession`/`applyChoice`で進め、
  次を返す。到着時の知覚（方針・効果ごとの予想・許容幅・実際値・ずれ・気づいたか・出来事を作ったか）、
  状態の変化（フラグ・変数・数値・所持品・出来事の作成と更新前後の値）、場面（本文の分解・選択肢ごとの条件判定・
  会話テンプレートごとの照合結果）。
- 本文の分解`traceText`: `resolveNarrativeDisplayText`の出力と、部分ごとの出所（物の性質と継承元・
  出来事・状態値・条件付きの文・差し込み文）。各部分はエンジンの`expandTemplateCore`で個別に展開し、
  連結が実行時の本文と一致しない場合は`exact: false`として分解を使わない。回数制限のある差し込みは、その文を表示した手で回数を記録する。道筋を戻ると残り回数もその手の状態に戻る。
- 条件`traceCondition`: 実行時の`evalCondition`の真偽と、読んだ値。`knowledgeRule`は
  `evaluateKnowledgeRule`の事実を付ける。`traceChoiceOrigins`は現在の選択肢の条件を、たどった各手の状態と照合する。判定が最後に変わった手があれば、判断欄にその手数と選んだ操作が出る。
- 物語全体の点検`checkModel(model)`: 開いている選択肢をすべて実際に選び、状態（場面・フラグ・数値・
  変数・所持品・出来事）単位で幅優先に調べる。結末までの道筋、行き止まり、一度も開かない選択肢、
  作られることのない出来事、解決できない参照、存在しない行き先、つながらない場面、実行時エラーを返す。
  時間条件があるときは最後の有効手まで、同じ場面でも手数を区別する。同じ出来事IDでも名前・性質の値が異なれば別の状態として調べる。状態数の上限（既定2000）で打ち切った場合は`truncated`。
- 記録は読み取り専用で、modelとsessionを変えない。人向けの文言は作業場が記録から組み立て、推測の文を足さない。

## 4. 作業場の画面（A案「判断を横に添える」）

- 実行: 左に本文と選択肢、右に「この場面でエンジンが判断したこと」（知覚のゲージ、状態の変化、本文の組み立て、
  選択肢が開いている理由・閉じている理由と開く方法）、本文の下にたどった道筋。本文の生成箇所は種類ごとに色を付け、
  押すと出所を出す。閉じた選択肢も理由付きで表示する。
- 点検: 物語全体を`checkModel`で調べた結果。結末と行き止まりは「この道筋を再生」で実行画面に再現する。
- 聞き込み見本「七人目の渡し賃」の実行では、開いた話題を本文と右の一覧から選べる。旅の手帳は現在の道筋に生じた出来事を順に載せる。「Studioで道筋・判断を見る」で同じ場面の条件や編集に戻る。
- 物語は一覧で見本を選ぶか、「物語のファイルを開く」またはJSONファイルのドロップで開く。一覧の「前提入力を開く」から試算した物語を別タブで開き、編集後に「物語を保存」で通常のJSONとして書き出せる。
- 編集（2026-11-21、その場で編集）: 実行画面の「この場面を編集」で本文の欄が編集欄に変わる。話者・本文・選択肢の文・行き先
  （新しい場面も作れる）・条件と効果を直すと、同じ道筋を再トレースして右列とプレビューがすぐ変わる。
  条件はフラグ・出来事・数値・変数・持ち物・物の性質・知識ルール（ルール本体の人物・物・分野・予想値もその場で）・
  すべて／どれか／満たさない（入れ子可）。効果は上記に加えて知覚（人物・物・分野・予想値・生まれる出来事）。
  場面ごとに「この場面に入った時の知覚」（知覚の方針）を足せる。「人物と物」の欄で人物の知識の分野・正確さ・許容幅、
  物の名前・親・性質と初期値、知識ルールの一覧を直す（使われている人物・物は消せない）。場面IDの改名は行き先・
  開始・方針へ追従し、場面の削除はそこへ行く選択肢と方針も一緒に消す（確認を出す）。点検の「どこからもつながらない場面」から
  も消せる。経過数（timeWindow）・変数の演算・移動の効果は文で表示し、削除だけできる。
  編集は`apps/studio/src/edit.js`の関数（値はモデル内の位置pathで指す）で行い、触っていない部分のキー順を保つ。
- 保存: 変更がある時だけ上部に「未保存の変更 n か所・保存」を出す。`models/`配下の物語は開発サーバーの
  `/__studio/save`で元のJSONへ書き戻す（エンジンの`loadModel`のスキーマ・整合検査に通らなければ拒否し、
  `models/`外は拒否）。保存前に点検を走らせ、結末数と問題数を結果に出す。手書き整形のファイルは初回保存で
  標準の2字下げ整形になり、その旨を表示する。ドロップしたファイルはJSONとして書き出す。

## 5. 受入の軸

1. JSONを読まずに、エンジンが何を判断したか（違和感・出来事・差し込み・選択肢の開閉）が分かる。
2. 画面のどの文も、元の事実（物の性質・条件・出来事・方針）へ1操作以内で遡れる。
3. 推測の文を出さない。
4. 記録はmodelとsessionを変えない。
5. 1440pxと768pxで読める。
6. 上部の常設操作は3つまで（物語・最初から・表示の切替。保存は未保存の変更がある時だけ出る）。

1・6はuserの目視で受け入れる。2〜4はエンジン試験（`test/trace.spec.ts`）で確かめる。
