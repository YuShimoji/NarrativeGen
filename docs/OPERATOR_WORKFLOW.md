# Operator Workflow

人間オペレーターの実ワークフロー・痛点・品質目標を保持する正本。

## 全体フロー

5ステージパイプライン (SP-PIPE-001):

1. **Stage 1: 構想・設計** -- テキストエディタ/ホワイトボードでストーリー骨格を設計 (100% 手動)
2. **Stage 2: コンテンツ制作** -- Web Tester でノード・選択肢・条件・効果を制作 (80% 手動 / 20% ツール支援)
3. **Stage 3: 検証・調整** -- バリデーション + 推論エンジン + プレイテスト (30% 手動 / 70% 自動)
4. **Stage 4: エクスポート** -- JSON / CSV / Yarn / Ink / Twine に出力 (10% 手動)
5. **Stage 5: ランタイム統合** -- Unity Editor 等にモデルを配置・接続 (60% 手動)

1人で3つの帽子 (Writer / TechDesigner / Integrator) を切り替えて全ステージを担当する。

Stage 2-4 は Web Tester 内で完結する。Stage 1 はツール外、Stage 5 は Unity Editor 等。

## 工程ごとの痛点

- **Stage 1 → 2**: 設計 (ビート表等) から Web Tester への移行が手作業。ビート表がそのままノードにならない
- **Stage 2**: テキスト編集エリアが小さい。長文執筆には不向き (WritingPage 連携で解決予定だが延期中)
- **Stage 4**: Dynamic Text 構文が JSON 以外のフォーマットで失われる (JSON 主軸戦略で回避)
- **Stage 4 → 5**: エクスポートファイルの Unity プロジェクトへの配置が手作業

## AI 監修から開発までの実運用

このプロジェクトでは、監修 AI が方向と成果条件を整理し、その Prompt を開発 AI に渡して実装する。標準ループは次の 5 段階とする。

1. **Orient**: 開発 AI がリモート同期と正本確認を行い、現在の artifact と bottleneck を復元する。既知情報の再質問はしない。
2. **Shape**: 高主観・高コストな方向だけ、監修 AI または開発 AI が異質な 2-4 案と最小の確認材料を出し、人間が方向を選ぶ。
3. **Build**: 監修 AI は成果契約を一つの Prompt で渡す。開発 AI は分解、実装、直接関係する修正を連続して完了する。
4. **Verify**: 自動検証と、必要な場合だけ一まとまりの目視レビューを行う。小変更ごとに手動確認を挟まない。
5. **Close**: 開発 AI が `HANDOVER.md` を現在形に更新し、要求・仕様・ロードマップに差分があれば各正本へ反映し、検証済み変更の git follow-through まで閉じる。

監修 AI は成果、現在の bottleneck、守る境界、受入シグナル、未決の高位判断を所有する。実装順序を細切れに指定したり、routine な継続許可を取り直したりしない。開発 AI は可逆な実装判断、関連修正、検証、状態同期を所有する。人間は高位の創造方向、感性評価、外部公開、契約変更を所有する。

### 解消すべき協働摩擦

- 安全確認が routine な実装継続まで止め、開発が進まない
- Prompt がファイル単位・確認単位に分割され、一つの成果が多数の往復になる
- 完了報告と次作業が複数文書に複写され、現在地が古くなる
- リポジトリを開かないと見られる現在地導線がなく、更新も完了条件に入っていない
- AI が選択肢や試作を出さず、大きな成果物を初見で提示してから微修正を反復する

最後の摩擦を避けるため、AI が創造作業そのものを奪わないことと、AI が調査・方向案・比較材料・低コスト試作を出すことを分けて扱う。方向選択は詳細化の承認であり、通常は実装承認ではない。現在の `IMPLEMENT` packet がその選択を最終 gate と明示した場合だけ、選択後の実装と polish を assistant-owned とする。それ以外は選択結果を spec/prototype に固定し、一度の高位 `IMPLEMENT` 承認へ渡す。同種の微修正が 3 巡した場合は微調整を止めてレイアウト、情報設計、または方向選択を再度開く。

## 品質目標

- 全モデルが `npm run validate` でスキーマバリデーション通過
- 推論エンジンの到達可能性分析で孤立ノードがゼロ
- 主要ルートのプレイテストが完了済み
- E2E テスト: 0 failed を維持
- TODO / FIXME / HACK: 0 を維持

## Actor Boundaries

- **user**: Stage 1 全般 (構想・キャラクター設計・分岐ロジック設計)、Stage 2 テキスト執筆・分岐設計、Stage 3 プレイテスト目視確認・BGM/画像の感性確認、Stage 5 Unity UI 接続の設計判断、UI 方向性判断
- **assistant**: ドキュメント作成・同期、コード実装、バリデーション設計、エクスポーター実装、テスト修正、方向比較のための調査・選択肢・低コスト試作、選択済み方向の UI/visual/language/motion 実装と polish
- **tool**: スキーマ検証 (自動)、構造検証 (自動)、到達可能性/パス/影響分析 (自動)、自動保存 (500ms debounce)
- **shared**: Stage 3 検証 (ツール自動 + 目視手動)、Stage 4 エクスポート (形式選択手動 + 変換自動)、次スライス選定、仕様策定

## 手動工程 / 自動化禁止工程

- ストーリー構想・テキスト執筆 (Stage 1-2 の創造的作業)
- プレイテスト目視確認 (Stage 3)
- BGM / 画像の感性確認 (Stage 3)
- Unity UI 接続の設計判断 (Stage 5)
- UI デザインの方向性判断

## 運用ルール

- 一度説明された workflow pain はここへ固定する
- 「本制作へ進む前に workflow proof が必要」な案件では、その proof 条件もここへ残す
- 一つの成果を閉じる実装を、調査・実装・関連修正・検証・状態更新の別 Prompt に分解しない
- 目視レビューは、方向選択前の比較と実装後の受入に集約する
