# Operator Workflow

人間オペレーターの実ワークフロー・痛点・品質目標を保持する正本。

## 全体フロー

制作ワークフローの正本は [SP-PIPE-001](specs/pipeline-workflow.md)（2026-11-22体系化）。工程は次の7つ。

1. **前提を置く** -- 物・人物・思い込み・場を定義する (人)
2. **組む** -- 前提から組む ([SP-PREMISE-001](specs/premise-driven-story.md)) か、Studio で手で組む
3. **判断を見る** -- Studio の実行で、エンジンの判断を右列で読む
4. **全体を点検する** -- Studio の点検で、結末・行き止まり・開かない選択肢を調べる
5. **直す・文章を書く** -- Studio のその場で編集。作品として採る文章は人が決める
6. **保存して守る** -- 保存時の検査、`npm run check:safety`、`npm run test:engine`
7. **出す・つなぐ** -- 出力と Unity 統合 (ゲーム層の凍結中は扱わない)

1人で3つの帽子 (Writer / TechDesigner / Integrator) を切り替えて全工程を担当する。

日常の作業は 3 → 4 → 5 の輪。世界の定義を変える時だけ 1 へ戻る。

## 工程ごとの痛点

- **1**: 前提ファイルは JSON の手書きで、数値を変えて比べる往復が遅い
- **2 → 5**: 前提から生成した物語を手で直すと、再生成と食い違う。育てる物語は Studio の「写して育てる」で `models/examples/` へ写す (2026-11-22 user)
- **5**: 会話テンプレート・言い換え辞書・経過数の条件を Studio で編集できない。長文執筆には不向き (WritingPage 連携は延期中)
- **7**: Dynamic Text 構文が JSON 以外のフォーマットで失われる (JSON 主軸戦略で回避)。出力ファイルの Unity への配置は手作業

## AI との開発の回し方

進め方の規則は [REPO_LOCAL_RULES.md](REPO_LOCAL_RULES.md)。ここには回し方と、繰り返したくない摩擦だけを置く。

1. **Orient**: リモートと正本を確かめ、今の成果物とボトルネックを復元する。分かっていることは聞き直さない。
2. **Shape**: 体験が分かれる方向だけ、異なる 2-4 案と最小の比較材料を出し、user が選ぶ。
3. **Build**: 選ばれた効果の範囲を、分解・実装・関連する修正まで続けて終える。選択の後に実装の承認を取り直さない。
4. **Verify**: 自動の検査と、必要な時だけ一まとまりの目視。小さな変更ごとに手動確認を挟まない。
5. **Close**: `HANDOVER.md` を現在形に書き換え、差分を各正本へ反映し、commit・push まで閉じる。

### 繰り返したくない摩擦

- 安全確認が通常の実装まで止め、開発が進まない
- 依頼がファイル単位・確認単位に分かれ、一つの成果が多数の往復になる
- 完了報告と次の作業が複数の文書に写され、現在地が古くなる
- 古い禁止や承認の手続きが残り、user が選んだ後も実装に入れない (2026-11-22 に整理)
- AI が選択肢や試作を出さず、大きな成果物を初見で出してから微修正を繰り返す

同じ種類の微修正が 3 巡したら微調整を止め、配置・情報の設計・方向の選択を開き直す。

## 品質目標

- 全モデルが `npm run validate` でスキーマバリデーション通過
- Studio の点検で、行き止まり・解決できない参照がゼロ
- 主要ルートのプレイテストが完了済み
- 前提から生成した物語が、実行時の再生で生成器の予測と一致する
- TODO / FIXME / HACK: 0 を維持

## Actor Boundaries

- **user**: 作品の前提の中身 (物・人物・思い込み・場・意図)、作品として採る文章、プレイテストの目視確認、表現と方式の採否、ゲーム層の再開と Unity UI 接続の判断、UI 方向性判断
- **assistant**: ドキュメント作成・同期、コード実装、検査の設計、テスト修正、方向比較のための調査・選択肢・低コスト試作、見本と試験用の前提・物語・骨子文・文章案、選ばれた方向の実装と仕上げ
- **tool**: スキーマ検証、違和感の判定、展開の列挙と割合、物語全体の点検、保存時の検査
- **shared**: 点検結果の読み取りと直す場所の決定、次スライス選定、仕様策定

## 人が行う工程

- 作品の前提の中身と、作品として採る文章を決めること (工程 1・5)
- プレイテスト目視確認 (工程 3)
- BGM / 画像の感性確認 (ゲーム層、凍結中)
- Unity UI 接続の設計判断 (工程 7)
- UI デザインの方向性判断

## 運用ルール

- 一度説明された workflow pain はここへ固定する
- 「本制作へ進む前に workflow proof が必要」な案件では、その proof 条件もここへ残す
- 一つの成果を閉じる実装を、調査・実装・関連修正・検証・状態更新の別 Prompt に分解しない
- 目視レビューは、方向選択前の比較と実装後の受入に集約する
